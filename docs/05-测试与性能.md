## 3. 压力/掉电测试工程

`test_apps/stress` 单独覆盖硬件极端场景：

```powershell
cd components/esp_sqlite3/test_apps/stress
idf.py set-target esp32c5
idf.py erase-flash      # 清空 NVS/SPIFFS，重置测试阶段
idf.py flash monitor
```

用例：

- **掉电复位**：连续 8 次在写事务进行中调用 `esp_restart()`；每次重启执行
  `PRAGMA integrity_check`，并校验 `power` 表行数始终是完整批次（16 的倍数）。
  这是“写入过程中硬件复位”测试；真实拔电仍需外部继电器/人工断电，但复位
  路径已覆盖 SPIFFS/WAL 恢复。
- **磁盘写满**：向 1MB SPIFFS 反复插入 16KB BLOB，确认返回 `SQLITE_FULL`/
  `SQLITE_IOERR`，清理后还能重新创建、写入、查询数据库。
- **只读挂载**：测试工程注册 `/ro -> /db` 的只读 VFS 包装器（
  `ESP_VFS_FLAG_READONLY_FS`），写打开返回 `EROFS`；SQLite 自动降级只读，
  查询成功，写入返回 `ESP_ERR_NOT_ALLOWED`。
- **mmap**：`PRAGMA mmap_size` 必须为 0（`SQLITE_MAX_MMAP_SIZE=0`）。
- **progress handler**：业务 handler 在 VACUUM 前后保持有效。

期望串口：

```
I (...) stress: power DB valid: rows=... (batch=16)
I (...) stress: power-loss cycles complete: 8
I (...) stress: disk full: writes=... err=ESP_ERR_NO_MEM sqlite_rc=13
I (...) stress: disk full: recovery ok (free=...)
I (...) stress: read-only VFS: write rejected (ESP_ERR_NOT_ALLOWED)
I (...) stress: read-only VFS mount: ok
I (...) stress: mmap=0, progress handler: ok (... calls)
I (...) stress: STRESS RESULT: PASS
```

### 4.5 失败时优先检查

1. SPIFFS 挂载是否成功（分区名 `storage`、挂载点 `/db`）；
2. 串口是否有 `SQLITE_CANTOPEN / SQLITE_IOERR_*`；
3. 是否误用了 MINIMAL 档位却期待 WAL/FTS5/RTREE；
4. 板子 Flash 是否真的是 4MB 以上（自测分区表需要 4MB）；
5. 任务栈是否足够（FULL 自测在 `app_main` 任务使用 32KB 栈；
   8KB/16KB 在无 PSRAM 的 C5 上会栈溢出或触发 OOM）；
6. 无 PSRAM 型号是否把默认页缓存降到了 8~16KiB，并避免同时打开
   多个 64KiB 缓存的连接。

## 5. 性能调优

### 5.1 参数

| 参数 | 默认 | 建议 |
|------|------|------|
| `page_size` | 4096 | Flash 4096；SD 卡可 4096 |
| `cache_size_kib` | 16 | 无 PSRAM 8~16；带 PSRAM 32~128，可到 256+ |
| `journal_mode` | 保持现有（新建 DELETE） | 读写并发用 WAL；纯配置用 DELETE |
| `synchronous` | FULL | 掉电安全优先；可接受丢最近事务用 NORMAL |
| `temp_store` | MEMORY | 排序大时注意堆 |
| `busy_timeout` | 5000ms | 多任务写可 10000ms |
| `wal_autocheckpoint` | 1000 页 | Flash 可设 256~512 |
| `PRAGMA optimize` | 手动 | 每日/联网空闲执行 |

### 5.2 写入模式

- **批量写必须用事务**：100 行逐条 commit 会产生 100 次 journal/fsync，
  事务内只产生 1 次；
- 预编译语句复用，避免重复 parse；
- 避免在事务中做网络/长延时操作，减少锁持有时间；
- 大导入可临时 `PRAGMA synchronous=OFF`，导入后恢复 `FULL` 并 `VACUUM`；
- 删除大量历史数据后，`VACUUM` 回收空间（需要额外空间）。

### 5.3 WAL 在 Flash 上的注意事项

- WAL 会额外写 `-wal` 文件，提交频繁时写放大明显；
- 长期运行建议：
  ```sql
  PRAGMA wal_autocheckpoint=256;
  ```
  并在空闲时 `wal_checkpoint(TRUNCATE)`；
- SPIFFS 磨损均衡有限，不要把高频日志无限追加到 DB；
- 只读导出场景用 `query_only=ON`，避免 WAL 写入。

### 5.4 性能基准建议

接板后可用以下 SQL 做基线（自测工程已包含类似逻辑）：

```sql
-- 建表
CREATE TABLE bench(id INTEGER PRIMARY KEY, v INTEGER, t TEXT);

-- 事务内 1000 行插入
BEGIN IMMEDIATE;
-- 循环 INSERT ...
COMMIT;

-- 点查
SELECT v FROM bench WHERE id = 500;

-- 范围查
SELECT count(*), sum(v) FROM bench WHERE id BETWEEN 100 AND 900;

-- 更新
UPDATE bench SET v = v + 1 WHERE id <= 100;

-- 全表扫描
SELECT count(*) FROM bench;
```

记录：

- 1000 行事务写入耗时；
- 1000 次点查耗时；
- 数据库文件大小；
- `PRAGMA page_count / page_size`；
- `freertos` 堆剩余（`esp_get_free_heap_size()`）；
- VFS 统计（`esp_sqlite3_vfs_get_stats()`）。

### 5.5 性能预期（经验值，需实测确认）

| 操作 | SPIFFS | FATFS/SD |
|------|--------|----------|
| 单行事务提交 | 10~50ms（受 fsync 影响） | 5~20ms |
| 1000 行批量事务 | 0.3~2s | 0.2~1s |
| 点查（有索引） | <1ms | <1ms |
| 全表扫描 10k 行 | 20~100ms | 10~50ms |
| VACUUM 1MB DB | 1~5s | 0.5~3s |

> 以上仅用于判断数量级，实际值取决于 Flash 型号、文件系统、页大小、cache、
> 是否 WAL、是否开启 fsync。

## 7. 已知未覆盖项

- 物理拔电/继电器断电（当前压力工程用 `esp_restart()` 覆盖 MCU 复位路径，
  真实掉电需外部断电治具）；
- 跨进程文件锁（ESP-IDF 单进程，VFS 只提供进程内锁）；
- mmap（未启用，`PRAGMA mmap_size` 始终为 0）；
- 无活动写连接时只读打开带未 checkpoint WAL 的库（无 shm 索引，需先由写连接恢复）；
- 动态扩展加载（无 dlopen）；
- 多核同时访问同一 DB 文件的长时间压力测试（双任务已实测，未做多核绑定/长时间老化）；
- 不同 Flash 品牌/文件系统的性能差异（需在目标板实测）。
