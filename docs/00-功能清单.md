# ESP SQLite3 当前功能清单

> 组件：`components/esp_sqlite3`
> 内核：SQLite 官方 **3.54.1** amalgamation
> 兼容：ESP-IDF v5.x ~ v6.x（已验证 v5.5.4 / v6.1）
> 适用芯片：ESP32-C5（RISC-V）；代码不含 Xtensa 专用指令，ESP32/S3/C3/C6 等同样可用

本文按“现在实际具备的能力”列清单。具体 API 签名见
[`03-API参考.md`](03-API参考.md)，VFS/锁/WAL 的实现细节见
[`02-架构设计.md`](02-架构设计.md)。

> **Flash 建议**：组件可在 4MB 自测工程中运行；并入主固件建议使用
> **8MB 及以上 Flash**，16MB 更宽裕。4MB 的 1.75MB app 分区放不下
> 主固件 + SQLite。

### 1.1 已移除的废弃 API

所有档位都定义了 `SQLITE_OMIT_DEPRECATED=1`，并且移除了共享缓存
（`SQLITE_OMIT_SHARED_CACHE=1`），不再提供以下接口：

| 已移除的 API | 替代方案 / 说明 |
|--------------|------------------|
| `sqlite3_aggregate_count()` | 无直接替代；自定义聚合函数请用 `sqlite3_aggregate_context()` 自行计数 |
| `sqlite3_expired()` | 无实际用途；用 `sqlite3_step()` 的返回值判断语句状态 |
| `sqlite3_transfer_bindings()` | 重新调用 `sqlite3_bind_*()` 绑定参数 |
| `sqlite3_global_recover()` | 原本就是空实现；SQLite 会自动处理内存分配失败 |
| `sqlite3_thread_cleanup()` | 原本就是空实现；SQLite 已不使用线程私有数据 |
| `sqlite3_memory_alarm()` | 用 `sqlite3_soft_heap_limit64()` / `sqlite3_hard_heap_limit64()` |
| `sqlite3_trace()` | 用 `sqlite3_trace_v2()` + `SQLITE_TRACE_STMT` |
| `sqlite3_profile()` | 用 `sqlite3_trace_v2()` + `SQLITE_TRACE_PROFILE` |
| `sqlite3_enable_shared_cache()` | 不提供共享缓存；每个连接使用独立页缓存 |

> **编译/链接差异**：
> - `sqlite3_aggregate_count`、`sqlite3_expired`、`sqlite3_transfer_bindings`、
>   `sqlite3_global_recover`、`sqlite3_thread_cleanup`、`sqlite3_memory_alarm`
>   的声明也被 `SQLITE_OMIT_DEPRECATED` 隐藏，调用会**编译失败**；
> - `sqlite3_trace`、`sqlite3_profile`、`sqlite3_enable_shared_cache` 的声明
>   仍保留在官方 `sqlite3.h` 中，但实现已被宏置 0，调用会**编译通过但链接失败**；
>   请不要使用这三个接口。

> `sqlite3_soft_heap_limit()` 虽然也标记为 deprecated，但 3.54.1 的实现没有把它
> 放进 `SQLITE_OMIT_DEPRECATED` 保护范围，因此**仍然可用**；建议改用
> `sqlite3_soft_heap_limit64()`。

## 8. 均衡擦写（wear leveling）说明

### 8.1 SQLite 本身是否做均衡擦写？

**不做。** SQLite 是数据库引擎，只负责页读写、日志、WAL、B-tree 更新；
它不知道底层是 NOR Flash、SD 卡还是文件系统，也不维护擦除计数。

均衡擦写由**底层文件系统/驱动**负责。本组件的 VFS 通过 ESP-IDF VFS 的
POSIX 接口访问文件，因此**继承底层文件系统的能力**，没有绕开它。

### 8.2 不同存储介质的均衡擦写能力

| 存储方案 | 均衡擦写 | 说明 |
|----------|----------|------|
| SPIFFS | ✅ 内建 | ESP-IDF SPIFFS 自身做磨损均衡；本工程自测默认使用它 |
| FATFS + wear_levelling | ✅ | 必须使用 `esp_vfs_fat_spiflash_mount_rw_wl` 等带 WL 的挂载方式 |
| FATFS 直接挂 raw Flash | ❌ | 没有 WL，频繁写会快速磨损；不推荐 |
| LittleFS | ✅ 内建 | 具备磨损均衡和掉电恢复；需通过组件方式加入工程 |
| SD 卡 | ✅ 由卡内控制器负责 | 对 ESP32 透明；但仍有写寿命，避免高频小写 |
| 外部 FRAM/EEPROM | 视器件 | 不是 SQLite 的典型存储介质 |

### 8.3 数据库写放大来源

即使文件系统有 WL，以下操作仍会增加擦写量：

- 每条自动提交事务都会写 journal + fsync；
- WAL 会额外写 `-wal` 文件；
- 页更新会重写整页（默认 4096B）；
- `VACUUM` 会重写整个数据库；
- `secure_delete=ON` 会把删除内容清零；
- `auto_vacuum` 会移动页；
- 高频 `PRAGMA optimize` / `ANALYZE` 也会写统计表。

### 8.4 建议

1. **批量写必须用事务**：100 条逐条提交会产生 100 次日志/fsync；
2. 预编译语句复用，避免重复解析；
3. 不要对高频日志无限追加；设置保留期并定期清理；
4. 长期运行设备建议 `journal_mode=DELETE` 或 WAL + 定期 `wal_checkpoint(TRUNCATE)`；
5. 不要频繁 `VACUUM`，只在空间碎片严重时执行；
6. 默认关闭 `secure_delete`；
7. 选择带 WL 的文件系统：SPIFFS、FATFS+WL、LittleFS；
8. 重要数据建议配合“写入次数/寿命”监控和外部备份。

> 结论：**均衡擦写有，但由文件系统提供，不是 SQLite 提供。**
> 本组件默认测试工程使用 SPIFFS，因此具备磨损均衡；如果换成 FATFS，
> 请务必使用 wear_levelling 挂载。

## 9. 为什么 Flash 占用这么大？

### 9.1 SQLite 不是“小型键值库”

SQLite 包含：

- SQL 词法/语法分析器；
- 查询规划器/优化器；
- 虚拟机（VDBE）；
- B-tree 实现（表/索引）；
- Pager/日志/WAL；
- 数据类型、排序、聚合、JSON、日期函数等；
- 可选 FTS5、RTREE、STAT4、DBSTAT、数学函数。

这些是“完整关系型数据库”的代价。当前 MINIMAL 静态库约 432KB，
CRUD 约 368KB，核心引擎本身就占主要部分。

### 9.2 全部档位实测（ESP32-C5，IDF 6.1，`-Os`）

同一最小示例固件：SPIFFS + 一次 CRUD smoke，**不含自测代码**。

| 档位 | 功能概述 | `libesp_sqlite3.a`（KB） | 示例固件（KB） |
|------|----------|--------------------------|----------------|
| MAX | 全部**未废弃**的可选功能（UTF-16/bytecode 虚表等） | 586.8 | 836.3 |
| FULL | WAL + FTS5 + RTREE + STAT4 + DBSTAT + 数学函数 | 569.9 | 818.7 |
| STANDARD | WAL + RTREE + DBSTAT + 数学函数 | 470.6 | 713.8 |
| MINIMAL | 核心 SQL + JSON，无 WAL/FTS5/RTREE/STAT4/DBSTAT/数学 | 432.4 | 648.4 |
| CRUD | 基础增删改查，关闭 JSON/日期函数/外键/完整性检查/WAL/FTS5 等 | 367.9 | 581.9 |

> 1 KB = 1024 B，保留一位小数。
> 上述是**静态库/示例固件**大小，不是主固件实际增加量。
> IDF 默认开启 `-ffunction-sections` + `--gc-sections`，链接时会丢弃未引用函数；
> 实际增加量通常小于静态库体积，具体以 `idf.py size` / map 文件为准。

### 9.3 全功能 vs 仅 CRUD 的最大/最小

| 配置 | 最小固件（`-Os`） | 最大固件（IDF Debug / `-Og`） |
|------|------------------|-------------------------------|
| MAX 全功能 | **836.3 KB** | **934.7 KB** |
| CRUD 仅增删改查 | **581.9 KB** | **650.1 KB** |

- 同一优化级别下，全功能比 CRUD 多约 **254KB**；
- 上述固件都包含 IDF/SPIFFS/最小示例主程序的固定开销，不只包含 SQLite；
- MAX 的静态库为 586.8 KB（`-Os`）/ 661.2 KB（Debug）；
- CRUD 的静态库为 367.9 KB（`-Os`）/ 412.1 KB（Debug）。

> CRUD 档位只关闭了当前 SQLite 3.54.1 amalgamation 下**可安全关闭**的
> 非 CRUD 能力；视图、触发器、ALTER、ATTACH、VACUUM 等因预生成 parser
> 限制仍会保留。它不是“理论上绝对最小”，但比 MINIMAL 再小约 65KB，
> 且能稳定编译链接。

### 9.4 与旧社区版的差异

旧社区版约 200~300KB，是因为：

- 使用 SQLite 3.25.2；
- `SQLITE_OMIT_FOREIGN_KEY`、`SQLITE_OMIT_INTEGRITY_CHECK`、
  `SQLITE_OMIT_WAL`、`SQLITE_OMIT_TEMPDB`、`SQLITE_OMIT_UTF16` 等大量裁剪；
- 日志放 RAM、锁/截断空实现；
- 单线程、无 FTS5/RTREE/STAT4/DBSTAT/数学函数。

本组件保留这些能力，因此体积更大；这是“功能完整”与“Flash 占用”的取舍。

### 9.5 还想更小怎么办？

CRUD 已是当前官方 amalgamation 下比较安全的激进裁剪；继续增加
`SQLITE_OMIT_VIEW/TRIGGER/ALTERTABLE/VACUUM/ANALYZE/...` 会在 3.54.1
预生成 parser 上出现未定义符号或编译错误，不建议直接改。
若确实需要更小，只能：

- 用 SQLite 源码重新生成匹配的 parser/amalgamation（工作量大）；
- 或退回旧版 SQLite（功能/安全性/掉电可靠性都会退步）；
- 或只把 SQLite 放在独立测试/诊断固件中，不并入主固件。

若目标是 4MB 双 OTA 且 app 只有 1.75MB，当前主固件已占约 1.50MB，
放不下 SQLite。**并入主固件建议使用 8MB 及以上 Flash**：8MB 可用双 2.5MB
OTA + 约 2.9MB 数据分区；16MB 更宽裕，可用双 4MB OTA + 4MB 数据分区。
示例分区表见
[`partitions/partitions_8mb_sqlite.csv`](../partitions/partitions_8mb_sqlite.csv)
和
[`partitions/partitions_16mb_sqlite.csv`](../partitions/partitions_16mb_sqlite.csv)。

## 10. 当前未实现/限制

- ❌ SQLite 自身不做均衡擦写（依赖文件系统）；
- ❌ 不支持跨进程文件锁（ESP-IDF 单进程固件，不需要）；
- ❌ 不支持 mmap（`SQLITE_MAX_MMAP_SIZE=0`）；
- ❌ 不支持动态 `.so` 扩展（无 dlopen）；
- ❌ 不提供共享缓存（`SQLITE_OMIT_SHARED_CACHE`）；
- ❌ 不提供已废弃 API（`SQLITE_OMIT_DEPRECATED`，清单见 1.1 节）；
- ❌ 未集成 SQLCipher/SEE 加密；
- ❌ 未集成 LittleFS 组件本身（需工程自行添加并挂载）；
- ⚠️ 硬件运行自测尚待接板验证（编译已在 IDF 5.5.4 / 6.1 通过）。
