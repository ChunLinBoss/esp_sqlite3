> 调研日期：2026-10-26

> 官方版本：SQLite **3.54.1** amalgamation
> SHA3-256：`92281c86e2957f9b9305890f9ac04204caa7b677cc868dc326d942689df28e30`（已校验）

## 1. 调研范围

| 来源 | 版本/状态 | 说明 |
|------|-----------|------|
| SQLite 官方 | 3.54.1 | `sqlite-amalgamation-3540100.zip`，Public Domain，唯一可信上游 |
| siara-cc/esp32-idf-sqlite3 | SQLite **3.25.2**（2018-09-25） | 最早的 ESP32 IDF 移植之一，Apache-2.0 |
| nopnop2002/esp32-idf-sqlite3 | 同上，fork | 修复 IDF5 构建、增加 PSRAM 与大量示例，但核心仍是 3.25.2 |
| ESP-IDF 官方仓库 | 无 sqlite3 组件 | v5.5.1 / v5.5.4 / v6.0.1 / v6.1 均未内置 `components/sqlite3` |

> 结论：ESP-IDF 并没有一个“官方旧版 sqlite3 组件”。工程里常说的旧版，实际上
> 是 siara-cc / nopnop2002 的 `esp32.c` + `sqlite3.c` 移植。

## 2. 社区版做了什么

### 2.1 目录与组成

```
esp32-idf-sqlite3/
├── sqlite3.c / sqlite3.h / sqlite3ext.h   # SQLite 3.25.2
├── esp32.c                                # 自定义 VFS + shox96 SQL 函数
├── shox96_0_2.c                           # 文本压缩算法（Apache-2.0）
├── sqllib.c / sqllib.h                    # db_open() / db_exec() 小封装
├── config_ext.h                           # 大量 SQLITE_OMIT_* 裁剪
└── CMakeLists.txt / component.mk
```

nopnop2002 版本额外提供：PSRAM 优先分配、ESP32-C 系列支持、IDF5 构建修复，
以及 `spiffs`、`fatfs`、`liitlefs`、`sd_mmc`、`sd_spi`、`tcp`、`udp`、
`websocket`、`mqtt`、`tusb`、`ftp`、`query`、`redirect`、`subquery` 等示例。

### 2.2 社区示例与 esp_sqlite3 的对应关系

| 社区示例 | 实际验证的能力 | esp_sqlite3 对应 |
|----------|----------------|-----------------|
| `spiffs` / `fatfs` / `liitlefs` / `sd_mmc` / `sd_spi` | 在 SPIFFS/FATFS/LittleFS/SD 上建库读写 | 原生支持；挂载点传给 `cfg.path` 即可 |
| `query` | 判断表/记录是否存在 | `esp_sqlite3_table_exists()`、`esp_sqlite3_query_int64()` |
| `subquery` / `subquery2` | 子查询/CTE | SQLite 3.54.1 原生支持（3.25 也支持） |
| `redirect` | 把 SELECT 结果通过 UDP/MQTT/HTTP 发出去 | 网络层与数据库解耦；用 `esp_sqlite3_query()` 回调取行后自行发送 |
| `tcp` / `udp` / `websocket` / `mqtt` / `tusb` / `ftp` | 通过网络/USB 传输 DB 文件或查询结果 | 用 `esp_sqlite3_vacuum_into()` 或 `esp_sqlite3_backup()` 导出，再交给现有网络组件 |
| shox96 压缩 | `shox96_0_2c/d` SQL 函数 | 原样保留 |

> 上述网络示例不是数据库内核能力，而是“取到数据后怎么发出去”。本组件把
> 数据库层做完整，网络传输继续用工程里现有的 `fm_ws`/HTTP/MQTT 即可。

### 2.3 旧版 VFS 的实际行为（重点）

| 能力 | 旧版实现 | 后果 |
|------|----------|------|
| 打开/读写 | `fopen/fseek/fread/fwrite` | 能用，但无法正确处理短读/短写、错误码不精确 |
| 文件锁 | `xLock/xUnlock` 直接 `return SQLITE_OK` | 多连接/多任务同时写会互相覆盖，数据库可能损坏 |
| 回滚日志 | 主库的 journal 放在 RAM 链表里（`esp32MemMethods`） | 掉电/复位时日志丢失，事务原子性失效 |
| 截断 | `xTruncate` 空实现 | `VACUUM`、日志复用等场景行为不正确 |
| 同步 | `fflush` + `fsync`（`SQLITE_NO_SYNC=1` 时完全跳过） | 掉电可能丢已提交事务 |
| 扇区大小 | `SPI_FLASH_SEC_SIZE` | IDF6 中该宏/头文件已变化，直接编译失败 |
| 设备特性 | 返回 0 | 保守但正确 |
| WAL | `SQLITE_OMIT_WAL` | 完全不可用 |
| 时间/随机数 | `time()` / `esp_random()` | 可用 |

### 2.4 旧版功能裁剪（`config_ext.h`）

旧版为了把 SQLite 塞进小 Flash，显式关闭了大量功能：

- `SQLITE_OMIT_FOREIGN_KEY`：外键约束不可用；
- `SQLITE_OMIT_INTEGRITY_CHECK`：`PRAGMA integrity_check` 不可用；
- `SQLITE_OMIT_TEMPDB`：临时表/临时库不可用；
- `SQLITE_OMIT_WAL`：WAL 不可用；
- `SQLITE_OMIT_UTF16`：UTF-16 API 不可用；
- `SQLITE_OMIT_LOAD_EXTENSION`：扩展加载不可用；
- `SQLITE_OMIT_SHARED_CACHE`：共享缓存不可用；
- `SQLITE_OMIT_AUTOVACUUM`：自动 vacuum 不可用；
- `SQLITE_OMIT_CAST`、`SQLITE_OMIT_CHECK`、`SQLITE_OMIT_CONFLICT_CLAUSE`、
  `SQLITE_OMIT_EXPLAIN`、`SQLITE_OMIT_ANALYZE` 等：SQL 能力被削减；
- `SQLITE_THREADSAFE=0`、`SQLITE_MUTEX_APPDEF=1`：单线程；
- `SQLITE_TEMP_STORE=1`：临时数据写 Flash；
- `SQLITE_DEFAULT_PAGE_SIZE=512`；
- `SQLITE_DEFAULT_LOOKASIDE=512,128`：每连接约 64KB lookaside；
- `SQLITE_DEFAULT_CACHE_SIZE=-1`：1KiB 页缓存（极小）；
- `SQLITE_NO_SYNC=1`：默认不 fsync。

> 注意：`SQLITE_OMIT_*` 是**编译期**裁剪，不是“运行时开关”。一旦按旧版配置
> 编译，`PRAGMA foreign_keys=ON`、`PRAGMA integrity_check` 等都不会生效。

## 4. 3.25.2 → 3.54.1 的主要 SQL 能力提升

除了上表，3.54.1 相对 3.25.2 还包含多年安全修复、查询优化器改进和以下常用能力：

- `VACUUM INTO`（3.27+）：一致性备份，不需要停止业务；
- `PRAGMA optimize`（3.18+，后续增强）：长期运行设备定期优化统计；
- `PRAGMA table_list`、`PRAGMA function_list`（3.30+/3.36+）；
- `RETURNING`（3.35+）；
- `STRICT` 表（3.37+）；
- JSON 内建、`->` / `->>` 运算符、JSON5（3.38/3.39+）；
- `iif()` 可变参数、`concat()` / `concat_ws()`（3.44+）；
- 聚合函数内 `ORDER BY`（3.44+）；
- `sqlite3_error_offset()`、`sqlite3_txn_state()`、`sqlite3_vtab_in()` 等 API；
- 大量 WAL、B-tree、查询规划器和内存管理 bug 修复。

> 对设备端最实际的意义：旧版的“日志放 RAM”在掉电时会直接破坏事务原子性；
> 新版本 + 新 VFS 才能谈“掉电安全”。

## 5. 体积实测（ESP32-C5，IDF 6.1，`-Os`）

统一使用同一个最小示例固件（SPIFFS + 一次 CRUD smoke，**不含自测代码**），
只切换档位；shox96 始终包含。

| 档位 | `libesp_sqlite3.a`（KB） | 示例固件 `.bin`（KB） | 静态 RAM（KB） |
|------|--------------------------|------------------------|----------------|
| MAX | 586.8 | 836.3 | 9.3 |
| FULL | 569.9 | 818.7 | 9.0 |
| STANDARD | 470.6 | 713.8 | 9.0 |
| MINIMAL | 432.4 | 648.4 | 7.6 |
| CRUD | 367.9 | 581.9 | 5.8 |

> 1 KB = 1024 B，保留一位小数。

最大/最小（同一固件，只改优化级别）：

| 配置 | `-Os` 最小 | Debug `-Og` 最大 |
|------|-----------|-------------------|
| MAX 全功能 | 836.3 KB | 934.7 KB |
| CRUD | 581.9 KB | 650.1 KB |

IDF 5.5.4 + MINIMAL 的自测固件为 691.7 KB（GCC 14.2），与 IDF 6.1 差异在 5% 内。

### 与主固件的 Flash 预算

当前 `FmC5Demo` 主固件约 **1536KB**，`ota_0/ota_1` 各 **1792KB**：

- MAX：1536 + 587 ≈ **2123KB** → 放不下；
- FULL：≈ **2106KB** → 放不下；
- STANDARD：≈ **2007KB** → 放不下；
- MINIMAL：≈ **1968KB** → 仍放不下；
- CRUD：≈ **1904KB** → 仍放不下。

因此**并入主固件建议使用 8MB 及以上 Flash**：

- 8MB：[`partitions/partitions_8mb_sqlite.csv`](../partitions/partitions_8mb_sqlite.csv)
  ，双 2.5MB OTA + 约 2.9MB SPIFFS 数据分区；
- 16MB：[`partitions/partitions_16mb_sqlite.csv`](../partitions/partitions_16mb_sqlite.csv)
  ，双 4MB OTA + 4MB SPIFFS 数据分区。

注意分区表变更不能只靠 OTA 下发，需要 USB 重新烧录一次。

## 6. 结论

1. 社区版的功能清单（SPIFFS/SD/FATFS、PSRAM、shox96、离线查询）我们已经全部覆盖，
   并补齐了旧版缺失的 WAL、外键、完整性检查、真实锁/日志/截断、JSON、FTS5、
   RTREE、STAT4、DBSTAT、数学函数、备份、迁移等能力。
2. 代码基线升级到官方 3.54.1，后续可以按“替换 amalgamation + 回归自测”的方式持续跟进。
3. 代价是 Flash 占用从旧版约 200~300KB 增加到静态库 **368~587KB**
   （CRUD~MAX）/示例固件 **582~836KB**（`-Os`），必须重新规划分区；
   这也是本方案没有直接改主工程 `partitions.csv` 的原因。
